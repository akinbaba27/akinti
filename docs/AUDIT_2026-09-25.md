### 2.2 Anon write access to two un-gated public tables · `2c48dfd` — NOT APPLIED

`supabase/migrations/20260925120000_lock_down_ungated_tables.sql`.

Every table in `public` is gated one of two ways: RLS with real policies, or
RLS enabled with zero policies (fail-closed). Two were neither:

- `public.schema_migrations` — created by this repo's own migration runner, so
  no migration ever enabled RLS on it.
- `public.rate_limit_actions` — `20260906140000` deliberately left RLS off as
  static reference data and granted `select`.

The gap is the same in both cases: Supabase ships a blanket
`grant all on all tables in schema public to anon, authenticated`, and a
migration that only *adds* `select` never takes the rest away. With RLS off,
those leftover INSERT/UPDATE/DELETE/TRUNCATE grants are live over PostgREST.

Confirmed against the live project with only the publishable (anon) key:
`GET /rest/v1/schema_migrations?select=name` returned real rows, while the
three fail-closed tables (`billing_events`, `play_events`,
`rate_limit_events`) correctly returned `[]`.

Impact beyond disclosure: `rate_limit_events.action` is a foreign key onto
`rate_limit_actions (action) on update cascade`, so an anonymous UPDATE
renaming a row (say `audio_upload`) cascades and makes `check_rate_limit` fail
for that action **for everyone** — a reachable denial of service on uploads,
comments, follows, messages, duet requests, reports, challenge entries,
checkout and flow events. An anonymous DELETE or TRUNCATE of
`schema_migrations` corrupts the ledger that decides which migrations are
pending.

The fix keeps every intended read path: `rate_limit_actions` keeps its
deliberate public `select` and loses all write privileges (RLS stays off on
purpose, exactly as 20260906140000 reasoned); `schema_migrations` loses every
client grant and gains fail-closed RLS. Safe for the runner, which connects as
the owning `postgres` role (`rolbypassrls = true`, verified).

**This migration is committed but not applied — the sandbox blocked the
`npm run db:migrate` that would have applied it. It needs one command from the
founder. See §6.1.** I did not write the destructive proof (an actual anon
UPDATE), so the DoS is established from the grant table plus the proven read
path, not from executing it.

### 2.5 Save, Block and Echo were not idempotent · `7eec934`

A Supabase `.upsert()` without `ignoreDuplicates` emits `ON CONFLICT DO
UPDATE`, which requires an UPDATE row-level security policy. `saves`, `blocks`
and `echoes` each expose SELECT/INSERT/DELETE policies only, so the conflict
path failed outright instead of being the no-op these toggles are meant to be.

Reproduced against the live project by replaying both statements as the
`authenticated` role with a real profile's JWT claims:

```
saves:  upsert-on-conflict FAILED -> 42501 new row violates row-level
        security policy (USING expression) for table "saves"
echoes: upsert-on-conflict FAILED -> 42501 ... for table "echoes"
...and both SUCCEEDED once switched to ON CONFLICT DO NOTHING.
```

Reachable without anything exotic: a double tap, a second tab, or
server-rendered "not saved" state that was already stale. Any second,
redundant write became a visible error.

Audited every other `.upsert()` in `src/lib/db`: `follows`, `open_calls`,
`push_subscriptions` and `challenge_picks` all have real UPDATE policies (and
`challenge_picks` deliberately replaces a row), so they are correct as
DO UPDATE and were left alone. Added `src/lib/db/toggleUpsert.test.ts` pinning
the option on all three toggles.

were already fully translated in both locales — they were simply never handed

### 2.7 Desktop dark theme kept 11 light-theme tokens · `50a8af9`

The desktop v3 "Akış" block (`@media (min-width: 1024px)` +
`:root:not([data-theme="light"])`) grounds and inks the page dark at ≥1024px
regardless of `prefers-color-scheme` — the founder's deliberate desktop
default (`docs/design/DESIGN_V3_DESKTOP.md`), and its own comment claims it
"wins over every token above wherever it conflicts". It did not: it set 23
tokens and left 11 more at their **light** values, because it sits outside the
`@media (prefers-color-scheme: dark)` block that defines them.

So on any desktop whose OS is set to light, with no explicit in-app light
choice, light hues rendered on a dark ground. The loud one: `--akinti-danger`
`#9a2e1e` on elevation-1 `#10171A` = **2.4:1**, an axe serious `color-contrast`
violation on the Settings "Log out" control — the single axe finding in the
whole first sweep, which is how this was caught. The rest were wrong in the
same direction and quieter: a pale mint `foam` as the unplayed trace,
near-black Atışma green and Cypher blue mode marks, a near-white
`signal-wash`, a light scrim behind sheets, light shadows carrying a light
hairline, and grain compositing with `multiply` (which darkens) instead of
`screen`.

Values copied verbatim from the dark block so desktop-dark and mobile-dark
stay one palette. `--akinti-signal-deep` and `--akinti-wave-rest` deliberately
not repeated — both are `var()` aliases onto tokens the block already sets.

Verified at 1280×800: `--akinti-danger` resolves `#f07a62`, the control
computes `rgb(240,122,98)`, and axe reports 0 serious/critical on
`/settings/account`, `/settings` and `/settings/appearance` (was 1).

### 2.9–2.12 Turkish was not first-class · `ccf3182`, `0dab2c5`, `a7fbf62`, `4167b99`

The Turkish sweep found four separate English leaks. `scripts/i18n-check.ts`
reported ".tsx surfaces clean" throughout all of them, because its scanner
reads JSX text and attributes — none of this copy was there.

**2.9 Notification preference categories** (`ccf3182`). Settings →
Notifications rendered entirely in English: all five category labels, all five
descriptions, the save error and the success toast. It was the one settings
form with no namespace of its own, with copy parked in two module-level
`Record<NotificationCategory, string>` maps the scanner does not look inside.
Added a `NotificationsForm` namespace (12 keys) and registered it in
`SETTINGS_MESSAGE_NAMESPACES`.

**2.10 Four page titles** (`0dab2c5`). Home, Search, Notifications and
Messages rendered their `<h1>` from the English-only `TERMS` constant, so a
Turkish session showed "Home", "Search", "Notifications", "Messages" as the
largest text on the screen with Turkish copy underneath. This is documented
debt, not an oversight — `docs/I18N.md` §4 keeps `TERMS` English because ~150
call sites import it as a compile-time constant, and leaves each one "ready
for whichever stage next touches a given screen to adopt". This audit is that
stage for these four. No new keys needed; the `Terms` namespace already
mirrors every key 1:1. Each file's `export const metadata = { title: TERMS.x }`
is deliberately left alone — a static metadata object is evaluated before any
per-request locale exists, so it needs the `generateMetadata` conversion §4
describes, not a swap. **The browser tab title therefore stays English on
those four routes.**

**2.11 The in-app notification list** (`a7fbf62`). Every notification title and
body came from `format.ts`'s `VERB`/`BODY` maps built out of `TERMS`, so a
Turkish reader saw a translated shell ("Bildirimler", "Tümünü okundu
işaretle") wrapped around an entirely English list: "@aaaaaa sent you a
message", "requested a Duet with your Wave", "Now following you." The module's
own doc comment said as much: "This module only turns that into English." Push
notifications were already key-based and locale-correct (`docs/I18N.md` §8.3);
the in-app list is a separate surface and had been missed.

Added a `NotificationFormat` namespace (31 keys, hand-written Turkish).
`formatNotification(n)` → `formatNotification(n, t)`; it stays pure, and its
single consumer `NotificationItem.tsx` supplies the hook. Turkish needed no
restructuring — verb phrases follow the actor name in both languages
("{actor} seni takip etmeye başladı"), and the untranslated domain nouns take
their Turkish possessive suffixes inline ("Wave'ini kaydetti"). Verified live,
grouping plural included: "AKINTI Curated ve 1 kişi daha Wave'ini kullanarak
bir Duet yayımladı".

**2.12 The messaging formatter** (`4167b99`). Same gap in the sibling module,
plus a worse one: the inbox showed "Duet Request" and "No messages yet", and
day separators and bubble times came out of `toLocaleDateString("en", …)` /
`toLocaleTimeString("en", …)` — **hardcoded English regardless of locale**, so
a Turkish reader got "Monday" and "2:45 PM" instead of "Salı" and "14:45".
Added a `MessageFormat` namespace (8 keys) and threaded both a translator and
the reader's locale through `formatMessagePreview`, `groupMessagesByDay` and
`formatMessageTime`.

In both 2.11 and 2.12 the test suites now build **real** next-intl translators
over the shipped message files instead of asserting hardcoded English, so they
fail if a key goes missing from either locale or an ICU plural is malformed.
Every original English assertion is unchanged and still passes — that is the
evidence the migration preserved the copy — with Turkish cases added on top,
including weekday localization (Tuesday vs Salı) and the 12-/24-hour split,
which would have caught the hardcoded `"en"` directly.

One deliberate tradeoff: both test files import `createTranslator` from
`use-intl/core` rather than `next-intl`. next-intl re-exports it via
`export * from "use-intl/core"` and that star re-export does not survive
Vitest's module resolution (`next-intl`'s is `undefined` there, `use-intl`'s is
a function). `use-intl` is next-intl's own core at the same locked version and
the import is test-only, so no `package.json` dependency was added.
